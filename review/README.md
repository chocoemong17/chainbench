# Review the published v0.2.0 — without chasing new versions

**Feedback thread: [actual reproduction reports, including failures](https://github.com/chocoemong17/chainbench/issues/28).**

This kit keeps the **already published v0.2.0** as its fixed target. It is not a new
ChainBench release. The package, version, tag and release files are unchanged.
CI reports are generated by maintainer-controlled automation, **not independent
reviewers**. Automated runs never count as outside adoption. No pre-recorded success
file is treated as proof that someone else ran this release.

## 1. Get the fixed inputs and inspect the helper

Download the wheel from the [v0.2.0 release](https://github.com/chocoemong17/chainbench/releases/tag/v0.2.0).
Save [review.py](review.py) into the same local folder using GitHub's Raw/Download
button. Read it before running it. It is a standalone standard-library script;
it does not install packages, call the network, upload results or execute commands
from a downloaded report. Its `collect` action only executes a fixed set of
commands using the current Python interpreter and the already installed package.

```text
Wheel: chainbench-0.2.0-py3-none-any.whl
SHA-256: 34173a4d0e2dc731602ec45db0c99acc17c27da26e702410d843194bbeaed069
Release commit: a5a274f9f5891a84cbb9acc4e2df8d1e0584491c
```

The digest is a fixed integrity reference, **not a digital signature**. Compare it
with GitHub's release-asset digest through a channel you trust. This kit does not
claim that the repository's releases are configured as GitHub immutable releases.

## 2. Use a new environment, not an editable checkout

Linux/macOS (Python 3.10–3.12):

```bash
python3 -m venv .venv
.venv/bin/python review.py verify-wheel chainbench-0.2.0-py3-none-any.whl
.venv/bin/python -m pip install ./chainbench-0.2.0-py3-none-any.whl
.venv/bin/python review.py collect --output my-review.json
.venv/bin/python review.py summary my-review.json
```

Windows PowerShell (example with Python 3.12):

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe review.py verify-wheel chainbench-0.2.0-py3-none-any.whl
.\.venv\Scripts\python.exe -m pip install ./chainbench-0.2.0-py3-none-any.whl
.\.venv\Scripts\python.exe review.py collect --output my-review.json
.\.venv\Scripts\python.exe review.py summary my-review.json
```

`pip install` may download NumPy. **The review helper itself is offline.** It uses
isolated Python subprocesses outside your working directory and checks all ten
installed package `.py` files against the published wheel. Editable installations
and different versions/modified package source are rejected. It does not audit
NumPy binaries, the Python interpreter, `.pyc` files or the entire machine.

Use a new output filename on each attempt. Existing files, including output
symlinks, are not overwritten. A failed attempt exits with code 2 and does not
leave behind a success bundle. You may report the failure instead of success.

## 3. What is actually checked

- The seven bounded numerical conditions and the separate INFO observation.
- All three fixed presets; saved configurations must repeat identically **within
  that environment**. Parameters, row counts, finite observations and termination
  semantics are checked rather than just looking for the word “success”.
- A separate tiny GD case: `Q=diag(1,4)`, `x*=(-1,1)`, `x0=(0,0)`, step `1/4`.
  The helper checks coordinates and gaps against hand-computed binary-exact values
  using only the standard library. This is one implementation test, not a theorem.
- Rejection of duplicate JSON keys and attempts to overwrite an existing file.

The resulting JSON contains public synthetic settings/results, package-source
hashes and OS/Python/NumPy labels. It deliberately omits names, email addresses,
home paths, hostnames, environment variables, timestamps and raw subprocess logs.
**Inspect it before sharing.** Error messages are intentionally short to avoid
leaking a local path; rerun the underlying command locally to diagnose a failure.

## 4. Compare recorded results without executing either file

Compare your own second run, or a report another person actually collected. The
comparison does not establish who generated a report or whether it was executed:

```bash
python review.py collect --output second-review.json
python review.py compare my-review.json second-review.json
```

Replace `python` with `.venv/bin/python` or `.\.venv\Scripts\python.exe` as above.
`compare` and `summary` need only Python's standard library, not an installed
ChainBench/NumPy. They never execute the configurations or file contents.

| Exit | Meaning | What to do |
|---:|---|---|
| 0 | `MATCH_WITHIN_TOLERANCE`: same recorded input bytes, compatible structure and close finite observations | Report what you actually ran; do not call it a proof |
| 1 | `DIFFERENT`: some data, text, structure or stopping history differs | Inspect the first differences and share a reduced example |
| 2 | Invalid/incomplete evidence, wrong source/version or local error | Correct the input/install or report the failure |
| 3 | `REVIEW_INPUT_DIFFERENCE`: numbers are close but generated input bytes differ | Human review required; do not claim bitwise reproduction |

The default comparison is the symmetric condition
`abs(a-b) <= max(1e-7 * max(abs(a),abs(b)), 1e-12)`, using `math.isclose`.
These are **chosen comparison tolerances for this small, modest-scale fixed suite**,
not theorem constants or appropriate defaults for all numerical tasks. Values
near zero can match under the absolute tolerance even when their relative error is
large. `--rtol 0 --atol 0` requests exact numerical equality. Do not widen tolerances
just to turn a difference into a green label. NaN/Infinity/missing observations,
empty suites, changed configs, wrong metrics and inconsistent CG stopping cannot
become successful comparisons. CG can legitimately stop on a different update
near its threshold; such a case is reported as a difference for inspection.

A source/config hash is not an attestation that somebody executed the code. Two
fabricated or copied reports could also compare equal. This helper does not prove
who ran them, their independence, scientific correctness, or a support application.

## 5. How the integration tests work

The `frozen release review` workflow downloads the pinned release wheel (not a new
candidate build), verifies its hash, installs it and invokes this collector twice
on Linux, Windows and macOS. A separate read-only job downloads those three CI
reports and compares Linux against Windows/macOS. Exit 3 is retained as an explicit
input-byte difference needing review; exit 1 or 2 fails the job. All comparison
reports are retained as CI artifacts. Nothing is auto-posted as user feedback.

The Python unit tests use **artificial schema fixtures** to test malformed and
changed data. Those are not numerical execution evidence; real released-wheel
execution, source hashes and the hand-computed oracle are exercised by the
separate integration workflow. No package version or existing release is changed.
